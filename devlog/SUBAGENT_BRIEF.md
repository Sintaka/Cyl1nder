# 子智能体协作前言

## 1. 一句话定位
你是被主进程（Codex 主管）派出去的子智能体，**只改任务书里列出的写集文件**。
合并 diff、更新版本号、更新 devlog 索引、跑全量验证、下 commit——这些都是
主进程的职责，不是你的。你做完自己的写集后回报即可，不要越界代劳。

**你唯一的对外通道是「结束本轮时交付的报告」**：你和用户之间没有直连，
**不要用提问工具**（详见 §7）。有疑问就写进报告并结束，主脑会看到并回答。

## 2. 写集纪律
- **只碰任务书列出的文件**，任务书没提到的文件一律不动。
- **不碰 `devlog/*`**——除非任务书明确把某个 devlog 文件列进了你的写集。
- **不改版本号**（`bridge/bridge/protocol.py` 的 `VERSION`、
  `web/src/app/app-config.ts` 的 `APP_VERSION`、任何注释里的 `v0.1.0xxxx` 字样）。
  原因：你不可能知道当前版本号是多少。本仓 `devlog/AGENT_QUICKSTART.md` 记录过
  子智能体在三轮任务里写错版本号三次（两次猜成历史号，如 `v0.1.00132`/`v0.1.00142`，
  一次学乖后留了字面占位符）——一律由主进程在合并时填。
- **不提交**：不要跑 `git add` / `git commit`，diff 留给主进程 review。
- **不起服务器**：本机 8375（桥）与 8376（vite）可能正在服务用户**未保存**的工作，
  杀掉或占用这两个端口会导致用户丢数据。看到已在跑的服务就直接连它测试，
  不要另起一份、也不要重启它。

## 3. 环境硬约束（实测踩出来的，按症状识别）
- **`npx` 不可用**：会撞 `StandardOutputEncoding is only supported when standard
  output is redirected` 直接起不来。改用下面「可用调用方式」里的直接命令。
- **不要把外部程序的 stdout 接进 PowerShell 管道**：`node ... | Select-String`、
  `& git ... | Out-File`、`pwsh -File x | Select-Object` 这类写法会报「拒绝访问」
  或上面那个编码错误。让命令直接输出到控制台自己看 `$LASTEXITCODE`，或者让工具
  自己写文件（如 `git diff --output=<path>`）。
- **可用调用方式**（cwd 必须对）：
  - pytest：cwd `bridge`，`.venv\Scripts\python -m pytest tests`
  - tsc：cwd `web`，`node node_modules/typescript/bin/tsc --noEmit`
  - vitest：cwd `web`，`node node_modules/vitest/vitest.mjs run`
- **`$ErrorActionPreference = "Stop"` 会把「找不到可执行文件」变成终止性错误**，
  PowerShell 会用自己的 exit 1 退出——如果你想要一个独立的错误码区分「工具本身跑不起来」
  和「工具跑起来了但报告了问题」，必须用 `try/catch` 包住外部命令调用，否则那条
  区分分支是死代码，永远到不了。

## 4. 写文件与中文
- 一律用 `write` / `edit` 工具写文本文件（UTF-8 无 BOM）；**不要用 shell 重定向
  写中文**（PowerShell here-string 走管道时默认按 ASCII/`$OutputEncoding` 编码，
  中文会变成字面 `?`）。
- 如果确实必须用 pwsh 写文件，显式 `-Encoding utf8NoBOM`。
- 读文件用 `read` 工具，不要用 `cat` 之类的 shell 命令。
- **写完必须自查**：`write`/`edit` 工具在内容超长时可能**静默截断**，留下的真实形态是
  字面 `[<数字> chars omitted]`（例如 `[1234 chars omitted]`）。检查时按这个正则匹配
  `\[\d+\s+chars\s+omitted\]`，**不要用裸子串 `chars omitted` 去查**——那会命中
  devlog 里正在讨论这条规则本身的散文。

## 5. 测试纪律
- 本仓 vitest 跑在 `environment: "node"`，**没有装 jsdom / happy-dom**。任何碰
  `document` / `window` 的代码在这个环境下 `import` 就会在模块加载期直接炸，
  无法单测。遇到这种情况，把纯逻辑抽成不依赖 DOM 的纯函数导出再测，或者把 DOM
  操作作为依赖注入进去；不要尝试给 vitest 装 jsdom（那超出你的写集，也不是本项目
  的既有约定）。
- **加了修复就要做变异测试**：故意把修复点改坏，确认**特定**的那条/那几条测试
  变红（不是笼统的「有测试红了」）；确认后还原代码，再确认全绿；还原后
  **grep 一遍确认没有留下变异标记**（不要留 `MUTATION-TEST` 之类字样在最终代码里）。
  一条在变异下仍然是绿的测试等于没测到东西，是装饰品，不算验证。
- 报告测试结果时给出**测试总数**（如「vitest 47 例，51 文件」），不要只说「测试通过」
  这种没有量级的空话。

## 6. 报告格式
回报里必须包含：
- 改了哪些文件（对照任务书的写集逐一列出）。
- 关键实现**逐字贴出**（不要用「加了一些逻辑」这种概括代替代码本身）。
- 每个验证命令的**结果与退出码**（tsc 输出、vitest/pytest 的通过数、`$LASTEXITCODE`）。
- 变异测试的具体红/绿（哪条测试在哪种变异下变红，还原后哪些变绿）。
- **不要报告没有做过的验证**。做不到就直接说做不到，以及卡在哪一步——
  编造一个「已验证」比承认「没验证」代价更大，会让主进程带着错误前提去合并。

## 7. 遇到阻碍怎么办

**禁止使用 ask-questions 一类的提问工具向用户提问。** 你没有和用户直接对话的通道 ——
提问工具在你这一层不会得到回答，只会把这一轮挂住。

**要问就写进结果里然后结束对话**：把问题作为报告的一部分输出，结束本轮即触发向主脑的交付，
主脑看到问题直接回答你（或带着答案重新派活）。**结束对话本身就是提问的送达方式**，
不需要额外的工具调用。

问题要写成主脑能一句话回答的形式：给出你的判断与备选项，而不是开放式的"该怎么办"。
```
【需要主脑确认】xxx 的两种改法：
  A. …（我倾向 A，因为 …）
  B. …
写集里没有 <file>，A 需要它 —— 请确认是否放宽写集。
```

如果任务书自相矛盾（例如写集里的文件天然做不到要求的事），或者写集范围不足以
完成任务，**停下来，把矛盾点写清楚后结束对话**，不要：
- 硬猜一个方案糊过去；
- 偷偷扩大写集去碰任务书没列的文件；
- 反复检查仓库状态"等"主脑改主意（**主脑不会在你这一轮里回话**，等待是白烧 token）。

本仓 devlog 记录过一个正确案例：一次任务书把写集限成单个文件，同时要求「测不到
就抽纯函数出来测」，但该文件本身有无条件的 `document.getElementById` 调用，
在 `environment: "node"` 下连 `import` 都会炸——这两条要求互相矛盾。子智能体没有
自己扩写集，而是停下来把矛盾报给了主进程；主进程核实后主动放宽了写集。
**这是期望行为，照做不算失败。**

## 8. 提交前卫生（你不用跑，但要知道会被查什么）
主脑合并你的改动前会跑 `node scripts/check-hygiene.mjs`，查新增行里的三类问题
外加工作树里夹在文件中间的游离 `U+FEFF`。四个退出码：
- `0` —— 干净（**通过时它不打印任何东西**）。
- `1` —— 发现问题（写工具截断残留 / 变异测试标记残留 / 疑似中文乱码 / 游离 BOM）。
- `2` —— `VACUOUS`，没有内容可查，空扫描不构成通过。
- `3` —— 工具自身失败（比如 git 没跑起来），这不是卫生结论，与 1 严格区分。

你不需要也不应该自己跑这个脚本或提交，但写代码时提前避开会被它打红的三类形态
（截断标记、变异标记、连续 3 个以上问号）能省一轮返工。
