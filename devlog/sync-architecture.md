# 同步架构与脏几何教训 / Sync architecture & dirty-geometry lessons

> 版本 0.1.00004 起。本篇回答"脏几何能否避免"：**能，且已根治**——同步/重建决策改为**内容对比**，不再依赖任何会失步的簿记。

## 一、事件回顾（为什么会脏）
- v0.1.00003 修复"Force Cook 触发无限循环"时，live 测试发现输出几何出现"脏 266 点"（等于输入0 网格），且新编辑拉不回来。
- 根因链条：
  1. 早期 web auto-run 会把"输入"原样回推成"输出"（passthrough 回显）；某次回显把 in0 的 266 点网格写进了桥的 out0。
  2. HDA 拉取并应用了它 → out0 变成 266 点，`last_rev` 记成对应 rev。
  3. 此后真正的编辑来了（rev 更大），但 HDA 用 `since=last_rev` 增量拉取，**rev 簿记认为"已消费"** → 永远拉不到"新"数据 → 266 永久保留。
  4. 尝试"存储内容哈希"修复：哈希也会失步——只要有任何**不经哈希更新**的路径写过几何（如回退分支/历史代码），哈希就与几何不一致，后续因"哈希匹配"而跳过重建。
- 结论：**凡是基于 rev/哈希等"旁路簿记"判断"要不要重建"，都可能失步**；失步后只能靠重启清脏。

## 二、根治：内容对比（当前实现）
- `_same_as_buffer(geo, buf)`：每次 cook 把**当前输出几何**序列化（点位置 + 曲线点序），与桥里该 role 的最新 buffer **逐点/逐曲线对比**；不同才 `clear + _build_detail`。
- 无存储哈希、无 last_rev 依赖（last_rev 仅作信息）。任何来源的脏写入，下一次 cook 都会被纠正。
- 实测：脏 266 在 Force Cook 后自动被桥内真实内容 [100,100,100] 覆盖。

## 三、配套（防止"脏"产生）
- bridge `put_outputs` 内容去重：与已存相同的输出不 bump rev、不广播（打断回显循环）。
- web auto-run 只在**输入内容变化**时跑；连接/重连时的首次 inputs 视为**回放**不触发网络（防回显覆盖用户编辑）。
- HDA 无新内容时**保留现有几何**（Force Cook 不再清空）。
- 桥重启自愈：`get_outputs_since` 在 `since>rev` 时返回全部；`/pending` 带 `reset` 标志；HDA 每次 cook 用 `since=0` 全量拉取 + 内容对比（天然免疫 rev 重置）。

## 四、架构原则（写入规范，避免脏架构影响开发）
1. **同步/重建决策一律基于内容**，rev 只作提示，绝不作"是否重建"的依据。
2. 任何写输出几何的路径，必须最终与内容对比逻辑一致（要么走内容对比，要么不写）。
3. **不依赖重启清脏**：系统必须自愈（内容对比即自愈）。
4. 桥重启（workspace 归零）不得破坏同步。
5. live 测试污染（旧线程/脏几何）不应成为判断依据——以干净环境（hython 冒烟/pytest）为准，必要时重启 Houdini 拿干净态。
