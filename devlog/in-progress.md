我 import 刚交付的 `release-step.mjs`，Node 报：

**改口才是错的。** 子智能体的收尾报告里写着：

## -50 我之前那次「vec3 写验证」写的是它本来就有的值（等于没验）

00172 那轮我"验证"了 vec3 写路径：`PUT [0.0153, 0.7108, 0.0]` → `{"ok":true}` → 读回一致。
**但那正是它当时已经有的值。** 一个什么都不做的实现也会通过这个测试 ——
我验的是「读回来还是原样」，不是「写进去生效了」。

本轮补了真正的往返（用完立刻还原用户的值）：

```
1) 原值        [0.0153, 0.7108, 0]
2) 写不同值    PUT [0.5, 0.25, 0.125] -> {"ok":true}
3) 读回        [0.5, 0.25, 0.125]          changed correctly = True
4) 还原        PUT [0.0153, 0.7108, 0] -> {"ok":true}
5) 确认        [0.0153, 0.7108, 0]         restored exactly = True
```

**判据**：写路径的验证必须写一个**与当前值不同**的值。
「写入后读回等于期望」在期望 == 原值时是恒真的，与实现无关。
这和「变异测试」是同一条纪律的两面 —— 变异是「改坏了必须变红」，
这里是「不改就必须看不到变化」；**两者都在问「这个测试有没有可能失败」**。

（顺带：这次也顺手证明了 §-41 修的那条批量写在真实 Houdini 上确实落地，
而不只是端点返回了 `ok:true`。）

## -49 查了「谎报成功」是不是系统性的 —— **不是**（阴性结果）

缺陷 6（`PUT channel-values` 对失败的写返回 `ok:true`）修完后，我怀疑同一形状散布在别处：
桥里有 **58 处** `return {"ok": True, ...}`。

**但真正可疑的形状要窄得多**：不是「返回 ok:true」，而是
**「做了一次可能失败的写，然后把请求里的值当成成功回执 echo 回去」**。
按这个判据只有三处候选，逐个读完 —— **它们都是对的**：

| 位置 | 实际写法 | 判定 |
|---|---|---|
| `mapping_routes.py:434-435` | `if not result.get("ok"): return {"ok": False, "error": …}` | 正确 |
| `mapping_routes.py:447-448` | 检查 envelope `status == "error"` 才往下走 | 正确 |
| `channel_routes.py:136-137` | `if not result.get("ok"): return {"ok": False, "error": …}` | 正确 |

它们最后那句 `return {"ok": True, "value": payload.value}` 回的是**请求值的 echo**，
但**前面确实校验过写成功了**，所以不是谎报 —— 只是「回执不是读回值」而已（可接受）。

**结论：缺陷 6 是 `channel-values` 那条批量路径的个案，不是系统性问题。**
根因也解释得通：那条路径是**逐通道批量**写，`_send_cv_pending` 算出了逐项错误却没往上带；
上面三处都是**单值**写，失败即整体失败，没有「部分失败」这个中间态可丢。
**只有批量接口才有「部分失败」，也才有把它丢掉的机会。**

记这条是因为**阴性结果同样值钱**：下次再有人怀疑这个形状，不必重新读 58 处 ——
判据是「批量 + 逐项错误」，单值写不用查。
